# Project Engineering Rules

- Keep store loyalty in an append-only receipt ledger with random card tokens and staff-only RPCs; share the order RPC's per-user advisory lock and balance calculation to prevent duplicate receipts and cross-channel double spending.
- Render the customer loyalty card on its own authenticated page linked from bottom navigation; keep the shared card presentation separate from point calculations so visual changes never alter rewards.
- Issue loyalty cards through an AFTER INSERT profile trigger, backfilling existing profiles without replacing tokens; account creation must not depend on visiting the loyalty page.

- Use row-level access rules and narrowly granted `SECURITY DEFINER` RPCs for order and role-sensitive workflows, so client-side writes cannot bypass server validation.
- Enforce IP bans from gateway request headers at both order RPC entry and every order insert; fail closed without an IP and compare all forwarded IP candidates as inet so forged prefixes and IPv6 formatting cannot bypass bans, while admin unban remains independent of order guards.
- Record the visitor address from `cf-connecting-ip` before `x-forwarded-for` and `x-real-ip`, because only the Cloudflare header is unspoofable; trusting a client-supplied forwarded header lets a banned customer order under an invented address.
- Keep app-shell service-worker registration in one production-only wrapper that excludes Lovable previews and uses network-first page navigation, so offline caching cannot strand visitors on stale app screens.
- Resolve access from protected user_roles; profile roles are compatibility mirrors changed only by validated RPCs, so editing a profile cannot grant privileges.
- Bootstrap the first administrator only through a locked, single-use reservation and a confirmed matching auth email; never grant the first signup administrator access.
- Keep catalogue media in CDN asset pointers and attach by existing product ID; supplementary gallery views do not create sellable variants or change order data.
- Use ProductPhoto for product detail and enlarged media; decode the displayed image before revealing it and preserve portrait framing so partial downloads and square cropping cannot hide the product.
- Derive administrator push content and recipients from a stored order; reserve custom delivery messages for authenticated internal calls, and prohibit anonymous IP probing to protect customer privacy.
- Startup shows only the static boot screen in index.html (no second React splash); its light logo is preloaded and revealed only after decode, so startup never shows a partial logo or adds delay.
- Centralize visual identity in semantic HSL tokens, shared controls and a project-owned logo pointer; presentation changes must not alter data or business workflows.
- Wrap customer page headers in CustomerHeader so the shared origin promise is integrated into the same sticky banner without duplicate badges; keep staff headers independent.
- Keep catalogue browsing public; require a session to add to cart and to check out, returning customers only to same-origin non-staff paths after login, so role destinations stay protected.- Group catalogue variants (e.g. drink flavours) through the nullable products.family field; each variant stays its own product so stock, price and availability are managed individually.
- Keep the custom domain connected through Cloudflare proxy mode (CNAME verification, proxied record) because the direct A-record IP is unreachable from Morocco; never re-point it to a direct A record or a different IP.
- Ship the Android store app as a Trusted Web Activity of the primary custom domain (the lovable.app host redirects there, which breaks verification), verified by public/.well-known/assetlinks.json; keep both upload and Play signing fingerprints there so the app opens without a browser bar.
- Resolve shop links through shopNavigationPath for AppLink and catalogue banners; keep current and legacy shop hosts inside the router so absolute internal links do not leave the Android app. Outbound staff emails target the primary verified domain directly.
- Catalogue cards and lists show photos through productThumbnail (pre-generated lighter CDN copies, same framing); product detail keeps the original. Regenerate thumbnails when adding product photos; unknown URLs fall back to the original.
- Staff order status, receipt, courier, item replacement/removal, availability and payment confirmations must go through the guarded staff RPCs, which recalculate totals server-side; employees never receive direct authority over protected order fields.
- Customer address selection uses a keyless Leaflet/OpenStreetMap map and device geolocation; preserve coordinates independently of manually entered address text so no geocoding credential is required.
- Use the shared Leaflet/OpenStreetMap view for operational and tracking maps; keep longitude/latitude conversion in open-map helpers and draw live courier routes as direct lines with haversine distance/ETA, because map display must never require a paid token or an external routing service.
- Keep the profile address book on its own authenticated customer page using the existing user_addresses records and AddressPicker; checkout reuses those records without a second address store.
- Keep the exact provider store polygon in a shared coordinate JSON for address maps and client validation, and mirror it in the guarded order database function; test coordinate parity and inclusive boundaries so display and acceptance cannot diverge.
- Persist per-article unavailable choices in the cart and atomically through the order-creation RPC; staff reads order-item preferences and server replacement guards respect them, with a nullable legacy fallback so historical orders remain unchanged.
- Post-delivery shop feedback uses configured shop phone/WhatsApp contacts and the full order reference, independent of an internal driver; both professional contact settings must be readable without admin access, while only admins can edit them. Opening WhatsApp is not confirmation that a message was sent.
- Render order delivery details from the stored address snapshot through OrderDeliveryAddress in customer, staff and admin views; never substitute subsequently edited address-book instructions.
- Keep checkout pricing/opening-hours derivation in useCheckoutSummary and staff order loading/live alerts in useStaffOrders; pages stay presentational so display totals and the order payload share one calculation.
- The Gestion till reaches loyalty only through the HMAC-signed pos-loyalty function (signature over timestamp.body, 5-minute window) and service-role-only pos_* RPCs; till operations are idempotent by sale/refund ID and refunds are compensating ledger rows, never deletions.
- Admin order status, manual driver assignment and customer cancellation go through update_staff_order_status, admin_assign_order_driver and cancel_my_order; screens never write orders or notifications directly.
- Zone minimum_order is checked on the article subtotal before delivery fee and discounts, pickup exempt, in both minimumOrderStatus and create_customer_order.
